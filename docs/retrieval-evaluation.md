# Offline evaluation семантического поиска

ClipTrace может отдельно оценивать dense E5 baseline: E5 кодирует
запросы и заранее размеченные фрагменты, после чего evaluator сравнивает порядок
результатов с relevance-разметкой. Видео, PostgreSQL и Faster Whisper для этого
не нужны — проверяется именно качество поиска по готовому тексту.

Этот evaluator не запускает production hybrid-цепочку PostgreSQL FTS → RRF →
cross-encoder → temporal NMS. Поэтому его метрики нельзя выдавать за end-to-end
качество текущего поиска. После изменения chunk boundaries fragment-ID qrels также
нельзя переиспользовать без пересборки кандидатов и проверки разметки; предпочтительный
следующий контракт для таких сравнений — relevant time intervals и temporal IoU.

## Запуск

```bash
uv run cliptrace-eval \
  --dataset eval/retrieval_smoke.json \
  --model-cache-dir data/models \
  --k 1 --k 3 --k 5
```

При первом запуске будет скачана зафиксированная в конфигурации ONNX-ревизия
`multilingual-e5-small`. Итог печатается в JSON и содержит агрегированные метрики,
версию модели и результаты каждого запроса.

Файл `eval/retrieval_smoke.json` — только небольшой технический пример. Он проверяет
формат данных и работоспособность evaluation pipeline, но **не является benchmark и
не подтверждает качество ClipTrace**. Для quality claims нужен отдельный набор
реальных транскриптов и запросов с независимой человеческой разметкой.

## Формат датасета

```json
{
  "version": 1,
  "name": "my-evaluation-v1",
  "corpora": [
    {
      "id": "meeting-001",
      "fragments": [
        {
          "id": "budget",
          "text": "В следующем квартале нужно сократить расходы."
        }
      ],
      "queries": [
        {
          "id": "cost-reduction",
          "text": "где обсуждают уменьшение затрат",
          "relevance": {
            "budget": 3
          }
        }
      ]
    }
  ]
}
```

Один corpus соответствует одному видео: production-поиск ClipTrace также
ранжирует фрагменты только внутри выбранного `video_id`.

Требования к данным:

- `id` corpus, фрагментов и запросов должны быть уникальны в своей области;
- тексты не могут быть пустыми;
- каждый ключ `relevance` должен ссылаться на фрагмент того же corpus;
- relevance grade — целое число от `1` до `3`;
- у каждого запроса должен быть хотя бы один релевантный фрагмент.

Рекомендуемая шкала graded relevance:

- `3` — фрагмент прямо отвечает на запрос;
- `2` — полезный релевантный контекст;
- `1` — частично релевантный фрагмент.

## Метрики

- `Recall@k` — доля всех размеченных релевантных фрагментов, найденных в top-k;
- `MRR@k` — обратная позиция первого релевантного результата, либо `0`, если его
  нет в top-k;
- `nDCG@k` — качество порядка с учётом graded relevance и скидки за низкую позицию.

Метрики усредняются по запросам. Per-query часть отчёта нужна для разбора ошибок:
агрегат показывает наличие регрессии, а конкретный ranking — её причину.

## Как собирать настоящий eval-набор

1. Выбрать несколько видео, представляющих реальные сценарии использования.
2. Зафиксировать transcript fragments конкретной версии chunking pipeline.
3. Составить запросы независимо от точных формулировок транскрипта.
4. Разметить релевантные фрагменты как минимум одним человеком; для спорных
   примеров использовать повторную проверку.
5. Хранить версию набора и не подбирать запросы под ответы текущей модели.
6. Сравнивать модели и retrieval-логику на одном и том же наборе с фиксированными
   фрагментами. Изменение chunking требует заново сформировать кандидатов и проверить
   соответствие relevance-разметки новым границам.

Evaluation retrieval не измеряет качество ASR. Ошибки распознавания речи следует
оценивать отдельно по размеченному аудио через WER/CER.
